摘要

问题。把一句自然语言问题翻译成能在业务数据库上直接执行的 SQL，难点不在 SQL 语法， 而在于模型要看懂几十张表之间的关联、不规范的列名，以及「合格率」这类只存在于业务约定里的口径。 在 BIRD 基准的真实业务数据库上，Qwen3-8B 直接作答的执行准确率只有 46.68%； 打开模型自带的思考模式可提升到 59.97%，但单次查询的推理耗时增加约 19 倍，交互式取数场景无法接受。

做法。本文记录一次完整的领域后训练。先用更强的模型生成推理过程与 SQL， 并把每一条放到真实数据库上执行、与标注结果比对，只保留结果一致的 5783 条作为训练数据； 在此之上做全参数监督微调；最后由微调后的模型自己采样，用执行结果判定正误， 构造 7989 对偏好数据做直接偏好优化。

结果。最终模型在 BIRD 开发集全量 1534 题上执行准确率达到 65.45%， 超过用于蒸馏的教师模型（60.67%），推理耗时约为思考模式方案的三分之一； 在完全未参与调参的 Spider 开发集上由 71.47% 升至 79.11%。 全部提升固化在一份 80 亿参数权重内，推理为单次调用，不引入检索、投票或重试等外部环节。

1. 项目背景#

自然语言取数是商业智能（Business Intelligence, BI）场景中的一类垂直指令任务：用户用中文或英文提问，系统需要在给定数据库上生成一条能真正跑出正确结果的 SQL。它与通用对话任务的差别在于，正确与否可以被客观判定——把 SQL 放到真实数据库里执行，与标准答案的结果集比对即可，无需人工标注，也无需大模型评判。

立项前先测了两件事，用来判断这个题目值不值得投入算力。

第一，基座模型确实不够用。Qwen3-8B 在 BIRD 开发集（11 个真实业务库、1534 题）上零样本直出 SQL 的执行准确率（Execution Accuracy, EX）只有 46.68%，语法有效率 84.22%。这些数据库并非简化的教学示例：financial（银行交易，8 表 68 MB）、thrombosis_prediction（医院检验，3 表 64 列）、european_football_2（570 MB）。

第二，提示词工程能够提升准确率，但代价不可接受。系统做了十余组免训练消融（表 1）。最强的可部署免训练配置是「打开原生思考模式 + 用标准建表语句表示数据库模式」，执行准确率 59.97%，但同一张 A100 上跑完 1534 题需要 1048.7 秒，是基准配置的 19.5 倍（成本细节见第 8 节）。商业智能取数是交互式场景，用户不会为一次取数等 20 倍延迟。

2. 任务目标#

目标是只优化模型自身，把上述提示词工程能拿到的收益固化进 80 亿参数的权重里，使模型在单次推理下达到甚至超过免训练最强配置的精度，同时把推理成本拉回可交互的量级。

2.1 输入与输出#

输入 = 自然语言问题
     + 数据库模式（M-Schema 表示：表名、列名、类型、主键，
                      每列附 3 个去重后的真实样例值）
     + 外部知识提示（BIRD 的 evidence 字段，90.4% 的题目带有）

输出 = 推理过程 + 一条可直接在该数据库上执行的 SQL

2.2 约束#

  • 只优化模型本身：所有提升必须固化在一份 8B 权重里，不引入检索器、选择器、投票器等外部组件。
  • 单次推理：头条数字只取贪心解码、一次调用的结果；多轮重试、多次采样投票即使有效也单独报告，不并入主线（第 7.5 节）。
  • 评测口径统一且不可事后调整：主指标为执行准确率，真实执行 SQL 并按 BIRD 官方的结果集集合语义比对；全量 1534 题不抽样；所有提升做配对麦克尼马尔精确检验（McNemar's exact test）与配对自助法 95% 置信区间；未达显著的结果一律显式标注，不作为结论引用；零人工标注、零大模型评判。

2.3 形式化定义#

本节出现的两个缩写按学术惯例给出全称：监督微调（Supervised Fine-Tuning, SFT）指用带标注的输入输出对做常规的有监督训练；直接偏好优化（Direct Preference Optimization, DPO）指用「同一问题的一条好回答与一条差回答」构成的偏好对直接优化策略模型，无需显式训练奖励模型。两者的完整设计动机分别见第 6.1 节与第 6.2 节。

任务。给定自然语言问题 q、数据库模式 S = {T1, …, Tm}（每张表含列名、类型、主外键与若干真实样例值）以及外部知识提示 e，模型 πθ 需生成一条 SQL 查询 y：

y ~ πθ( · | x ),    x = Prompt( q, S, e )

评价函数。设 D 为目标数据库，Exec(y, D) 为执行 y 得到的结果集，y★ 为标注 SQL。执行匹配的指示函数定义为

𝟙EX(y) = 1，当且仅当 Set( Exec(y, D) ) = Set( Exec(y★, D) )；否则为 0
（执行报错、超时均计为 0）

执行准确率即该指示函数在评测集上的均值：EX = (1/N) Σi 𝟙EX(yi)。采用集合语义而非逐行比较，与 BIRD 官方口径一致，代价是对行序不敏感（见第 9.3 节）。

优化目标与约束。

maxθ  E(q,S,e) [ 𝟙EX(y) ]    s.t. y ~ πθ( · | x )，单次采样，|θ| = 8 × 109

约束的实质含义是：不允许多次采样投票、不允许执行反馈重试、不允许外部检索或流水线编排，所有性能提升必须体现在权重 θ 内。

可验证蒸馏。设教师模型 πT 对训练问题 xi 生成推理过程与查询 (ci, yi)。构造训练集时施加执行一致性约束：

DSFT = { (xi, ci, yi) : 𝟙EX(yi) = 1 }

与常规思维链蒸馏 D = {(xi, ci, yi)} 的区别在于：过滤信号来自环境执行结果而非模型自评，因而能够识别「语法正确、逻辑自洽、但答非所问」的样本。监督目标为自回归交叉熵，且仅在回答段计算损失：

LSFT(θ) = − Σt ∈ Ans log πθ( zt | z<t )

其中 Ans 为回答段的 token 下标集合。提示词段（数据库模式约 2500 token）占序列的绝大部分，实测参与损失的 token 仅占 15.50%；若不做掩码，损失将主要由「复述数据库模式」贡献。

偏好优化。以监督微调后的模型对每个训练问题采样 K = 16 条候选，按执行结果划分为正例集与负例集：

Y+i = { y : 𝟙EX(y) = 1 }，   Y−i = { y : 𝟙EX(y) = 0 }

仅当两个集合均非空时该问题可用（实测可用率 28.54%）。正例取执行正确者中最短的一条；负例的选取方式是本项目的对照变量：

y−相似 = arg maxy ∈ Y− sim( y, y+ )，   y−相异 = arg miny ∈ Y− sim( y, y+ )

直接偏好优化的损失如下，其中参考模型 πref 取监督微调后的模型而非原始基座（理由见第 6.2 节），对数似然同样只在回答段累加：

LDPO = − log σ ( β [ log πθ(y+|x) / πref(y+|x) − log πθ(y−|x) / πref(y−|x) ] )

5. 数据构造：可验证蒸馏#

整套方法建立在一个前提上：存在一个确定性的、可自动调用的正确性判据。 在本任务中这个判据就是「把 SQL 放到真实数据库上执行，比较结果集」。 它同时被用在三个地方——评测、训练数据过滤、偏好数据构造，因此必须先把它做对。

import sqlite3


def exec_rows(sql: str, db_path: str, timeout_s: int = 30):
    """执行一条 SQL，返回结果集；不可执行时返回 None。"""
    conn = sqlite3.connect(db_path)
    conn.execute("PRAGMA busy_timeout = %d" % (timeout_s * 1000))
    try:
        rows = conn.execute(sql).fetchall()
        return set(rows)          # 集合语义，对齐 BIRD 官方实现
    except Exception:
        return None               # 语法错误、列名不存在、超时等一律计为不可执行
    finally:
        conn.close()


def is_correct(pred_sql: str, gold_sql: str, db_path: str) -> bool:
    """执行匹配：预测与标注的结果集相同才算正确。"""
    gold = exec_rows(gold_sql, db_path, timeout_s=300)   # 标注放宽超时
    if gold is None:
        return False              # 标注本身跑不通的题目直接排除，不计入分母
    pred = exec_rows(pred_sql, db_path, timeout_s=30)
    return pred is not None and pred == gold

三点工程注意事项。其一，超时刻意设置为不对称：标注 300 秒、预测 30 秒。 放宽标注只是为了拿到「正确答案是什么」这个参照，预测端仍然从严，净效果是模型必须写出不慢于标注的等价查询。 其二，集合语义对行序不敏感，因此漏写 ORDER BY 但结果集相同的查询会被判为正确； 沿用官方语义是为了数字可以横向比较，代价在第 9.3 节如实列出。 其三，评测器上线前必须自检：把标注答案当作预测跑一遍，执行准确率必须为满分，否则说明评测器本身有偏差（第 10.1 节）。

5.1 教师模型能力校准#

蒸馏之前需要先测定教师模型自身的水平，它决定了纯模仿路线的上限。 测定时有一个必须注意的设置：对于混合推理模型，生成预算由推理过程与答案共同占用， 若按普通任务的经验值设置，推理过程会占满额度而使答案缺失，且被截断的恰好是最难的样本， 其表现与「模型能力不足」无法区分。本项目将生成预算设为 8192，截断率降至 2.67%。

在此设置下，教师模型 DeepSeek-V4-pro 在 BIRD 开发集上的执行准确率为 60.67%， 语法有效率 96.13%。这个数字在后文反复出现：它是监督微调所能达到的上限， 也是判断「是否需要引入偏好优化」的依据（第 7.1 节）。

5.2 全量蒸馏与执行过滤#

教师对 BIRD 训练集逐题生成（推理链, SQL），随后在真实数据库上执行，结果集与标准答案一致才入库。9428 题原始数据中，有 350 题的标准答案自身就跑不通（3.7%，无法验证，予以排除并显式报告），可蒸馏基数为 9078 题，最终保留 5783 条（63.70%）。API 用量为提示词 1572 万 token + 生成 415 万 token（其中推理占 94%），120 并发下墙钟 651 秒。

损失掩码是这一步最容易静默出错的地方。一条训练样本里，提示词段（数据库模式约 2500 个 token）占绝大多数， 回答段只占少数。若不做掩码，交叉熵损失会主要由「复述数据库模式」贡献，真正想学的「怎么写这条 SQL」被稀释到几乎看不见。 实测参与损失计算的 token 仅占 15.50%。实现上只需把提示词段的标签置为忽略值：

IGNORE_INDEX = -100  # PyTorch 交叉熵的默认忽略值


def build_example(tokenizer, prompt_text, answer_text, max_len=5120):
    """构造一条监督微调样本，只在回答段计算损失。"""
    prompt_ids = tokenizer(prompt_text, add_special_tokens=False).input_ids
    answer_ids = tokenizer(answer_text, add_special_tokens=False).input_ids
    answer_ids = answer_ids + [tokenizer.eos_token_id]

    input_ids = (prompt_ids + answer_ids)[:max_len]
    # 提示词段全部置为 IGNORE_INDEX，反向传播时不产生梯度
    labels = ([IGNORE_INDEX] * len(prompt_ids) + answer_ids)[:max_len]
    return {"input_ids": input_ids, "labels": labels}


def loss_token_ratio(batch):
    """上线前必须核对的一个数：真正参与损失的 token 占比。"""
    total = sum(len(x["labels"]) for x in batch)
    counted = sum(sum(1 for t in x["labels"] if t != IGNORE_INDEX) for x in batch)
    return counted / total          # 本项目实测约 0.155

训练前做了三层验证，成本从低到高依次是：零件级（纯 CPU，核对掩码、截断率与提示词一致性）、 代码级（2 张卡加轻量优化器跑通完整训练循环与数据分片）、生产级（真实配置跑 4 步，看显存余量）。 这套顺序的意义在于：一次六卡训练要一小时量级，把可以用 CPU 发现的错误留到生产级才暴露是纯粹的浪费。

关于验证损失的一点说明。图 4 只有训练损失，因为本项目没有把验证损失作为选型依据，也就没有记录它。 原因是在这个任务上，损失与下游指标并不单调相关：损失衡量的是「与参考答案逐 token 对齐的程度」， 而执行准确率衡量的是「查询结果是否正确」，同一个问题的多种正确写法在损失上是被惩罚的。 所有选型决策一律以开发集上的执行准确率为准。这是取舍而非疏漏——代价是无法用验证损失做早停， 本项目改用固定训练轮数（2 轮）并在开发集上评测每个候选。

6.2 偏好优化#

方法定位：离线、同策略，不是在线偏好优化。本项目的偏好数据由监督微调后的模型一次性批量采样并落盘，训练过程中不再重新采样，因此属于离线直接偏好优化（offline DPO）。但采样来自被优化模型自身，数据是同策略的（on-policy），这与「用另一个更强的模型或人工标注生成偏好对」的常见离线设定不同——后者学到的是别人的偏好，前者纠正的是自己的错误。真正的在线偏好优化需要在训练过程中用当前策略即时采样、即时判定奖励并立刻更新，本项目没有这样做，原因是每次重新采样 16 条需要独立的推理作业，在共享集群上与训练作业交替排队的代价过高。第 7.3 节报告的第二轮属于迭代式（iterative）：用第一轮训练后的模型重新采样、重新构造偏好对再训一轮，介于离线与在线之间；其结果不是简单的「变差」，详见第 7.3 节。

偏好对由微调后的模型自采样 16 条 + 执行验证构造：结果集正确的作正例，错误的作负例。初始配置（2923 对、60 个优化器步、学习率 5e-7）的输出与基座逐字相同（Δ=+0.00，未达显著）。在同一批偏好数据上分别用基座与训练后模型打分可以确认，问题不在算法选择，而在训练强度不足——60 个优化器步、学习率 5e-7 不足以让权重产生可观测的变化。最终配置见表 6。

构造偏好数据与选取负例的核心逻辑如下。相似度用词面 Jaccard 系数， 计算开销可以忽略，且不引入额外模型：

def jaccard(a: str, b: str) -> float:
    """两条 SQL 的词面相似度。用于给正例挑选最接近的负例。"""
    ta, tb = set(a.lower().split()), set(b.lower().split())
    if not ta or not tb:
        return 0.0
    return len(ta & tb) / len(ta | tb)


def build_pairs(samples, gold_rows, neg_select="similar", max_pairs=4):
    """由同一问题的 K 条采样构造偏好对。

    samples : 模型对同一问题采样得到的 K 条 SQL
    gold_rows: 标注 SQL 的执行结果集，用于判定正误
    """
    good = [q for q in samples if exec_rows(q) == gold_rows]   # 执行结果一致
    bad = [q for q in samples if exec_rows(q) != gold_rows]
    if not good or not bad:
        return []                      # 全对或全错的问题无法构造偏好对

    chosen = min(good, key=len)        # 正例取执行正确者中最短的一条
    if neg_select == "similar":        # 本项目采用
        bad.sort(key=lambda q: -jaccard(chosen, q))
    elif neg_select == "dissimilar":   # 对照组
        bad.sort(key=lambda q: jaccard(chosen, q))
    return [{"prompt": ..., "chosen": chosen, "rejected": r} for r in bad[:max_pairs]]

「全对或全错的问题无法构造偏好对」这一行决定了数据产量：实测只有 28.54% 的训练问题可用。 这也解释了第二轮迭代为什么难以为继——模型变强后，能同时采出正例与负例的问题越来越少，可用率由 28.54% 降到 17.38%，偏好对减少 35%（第 7.3 节）。

图 5 里有一个值得单独指出的现象：隐式奖励间隔由 −39.4 升至 290.7， 偏好优化损失从 0.686 降到 0.034，训练在数值上非常"成功"，但最终执行准确率只提升 5.87 个百分点。 原因在于偏好优化直接作用于「正例与负例这两条固定字符串的相对排序」， 而评测指标取决于贪心解码实际生成的那一条——两者并不等价。 第一轮实验里 92.5% 的贪心输出逐字未变，正是这一点的极端表现。因此判断偏好优化是否生效， 必须在固定数据集上做端到端评测，不能看训练日志。

损失函数与对数似然的实现如下。seq_logp 有一处必须做的显存优化：

import torch
import torch.nn.functional as F


def seq_logp(logits, labels, ignore_index=-100, chunk=1024):
    """逐序列对数似然，只在 labels != ignore_index 的位置累加。

    直接写 log_softmax(logits.float()) 会物化 [B, T, V] 的浮点张量。
    以本项目的规模计算：2 x 8192 x 151936 x 4 B 约 9.96 GB，单个张量就会让反向传播显存溢出。
    改用等价形式 logp = z_y - logsumexp(z)，只产出 [B, T]，再按序列维分块，
    把瞬时峰值压到原来的若干分之一；每块的中间量各自入计算图，与一次算完等价。
    """
    logits, labels = logits[:, :-1], labels[:, 1:]
    mask = labels != ignore_index
    safe = labels.masked_fill(~mask, 0)

    parts = []
    for i in range(0, logits.size(1), chunk):
        lg = logits[:, i:i + chunk].float()
        tgt = lg.gather(-1, safe[:, i:i + chunk].unsqueeze(-1)).squeeze(-1)
        parts.append(tgt - torch.logsumexp(lg, dim=-1))
    token_logp = torch.cat(parts, dim=1)
    return (token_logp * mask[:, :token_logp.size(1)]).sum(dim=-1)


def dpo_loss(pi_chosen, pi_rejected, ref_chosen, ref_rejected, beta=0.1):
    """直接偏好优化损失。参考模型取监督微调后的权重，不是原始基座。"""
    logits = (pi_chosen - ref_chosen) - (pi_rejected - ref_rejected)
    return -F.logsigmoid(beta * logits).mean()

参考模型必须是监督微调后的权重而非原始基座。参考模型定义了「不允许偏离多远」的锚点； 若用基座做锚，监督微调阶段学到的能力会被 KL 项一并惩罚掉。 同理，对数似然只在回答段累加：两条候选共享同一段约 2500 个 token 的提示词， 把它算进去会把正负例之间的差异稀释到看不见。

作为横向对照还实现了组相对策略优化（Group Relative Policy Optimization, GRPO）。二值奖励下 67.69% 的采样组全对或全错、组内优势恒为 0，因此按 Reasoning-SQL 的做法加入稠密奖励分量（可执行性、模式 F1、n 元语法（n-gram）相似度），封顶 0.3，不压过主奖励 1.0，可用组比例从 28.6% 提升到 52.6%。其余超参：学习率 1e-6、裁剪范围 0.2、KL 惩罚系数 0.02（k3 估计量，恒非负）、每题采 16 条。

10.1 评测器先于一切#

项目的第一件事是把尺子造准：用标准答案当作预测跑自检，1219 题中 1218 题通过（99.92%）；唯一未通过项追到底是标准答案自身需要跑 128 秒触发超时，不是评测器的缺陷，因此已知的不可达上界为 0.08%。据此修正超时口径后，在全量 1534 题上重跑自检得到 100.0%，评测器本身不再引入误差。这次自检一次性暴露了三类隐藏问题：超时语义、标准答案数据质量、SQL 抽取逻辑。超时刻意设置为不对称——预测 SQL 30 秒、标准答案 300 秒，方向是对模型更严。

数据获取环节做了两道校验：按服务端返回的 Content-Length 精确校验字节数（只判「文件非空」会把中断产生的截断文件误认为完成）；从两个独立来源各下载一份开发集，对（题号, 库名, 问题, 归一化 SQL）计算 SHA-256，结果逐题完全一致。

10.2 训练前的三层验证#

一次失败的六卡训练要浪费 1.5 小时，因此每次训练前按三层递进验证：零件级（纯 CPU，不训练；验证损失掩码、截断率、提示词一致性）→ 代码级（2 卡 + SGD 优化器，跑通完整训练循环与数据分片）→ 生产级（4 卡真实配置跑 4 步，看显存余量）。

10.3 共享集群上的调度经验#

显卡数与 CPU 核心数是两个独立配额，只按显卡数算并发度会让一半算力闲置：

训练分区配额：6 GPU + 48 CPU 核（两个独立维度）

  --cpus-per-gpu=16 × 3 GPU = 48 核  →  CPU 配额用尽，剩余 3 张卡无法并发
  --cpus-per-gpu=8  × 3 GPU = 24 核  →  两个 3 卡作业可同时跑满

另一条经验是减少作业数比减少计算量更值钱：vLLM 加载一次 80 亿参数模型需 6.5 分钟（文件系统争用时可达 9 分钟），十余组免训练消融若拆成 10 个作业，光加载开销就是 65 分钟外加 10 次排队，因此合并为一个作业循环跑完。

10.4 沉淀下来的工程纪律#

  • 混合推理模型的生成预算必须按「推理过程 + 答案」合并设置，否则推理过程会占满额度而使答案缺失。
  • 训练端与评测端共用同一份提示词代码，否则蒸馏出的推理链会引用学生看不到的信息，等于训练时教模型编造。
  • 改显卡数必须同步改梯度累积，锁死有效批量；4 卡 × 8 与 6 卡 × 8 是两个不同的训练配置。
  • 训练过程中定期保存检查点，不要把长时训练的全部结果押在最后一次写盘上。
  • 单样本训练日志不能用来下任何结论；怀疑数值异常时，先查产生这个数字的显示逻辑。
  • 按数据库编号而不是按题目划分训练与验证集，否则同一数据库的模式与取值会造成泄漏。

11. 后续工作#

  • 推理链的正确性验证。可验证蒸馏只校验了答案，没有校验推理过程；下一步计划对训练集做人工抽检，量化"推理写错但 SQL 恰好正确"的比例。
  • 训练前置于思考模式之上的可能性。本项目的偏好数据构造在关闭思考模式的模型上进行；若在思考模式输出上构造偏好对，采样与训练成本约为当前的三倍以上，受算力预算限制未做，属于未验证的对照而非已证无效的方案。
  • 教师答错的 3295 条难题仍是未利用的存量，需要与「多采样」和「反向合理化」都不同的第三条路线。

以下八条是从本项目的具体实验中抽象出的一般性结论，每条都给出本项目内的实测依据。它们的适用范围不限于 Text2SQL。

原理实测依据
一、环境反馈优于模型自评在具备可执行环境的任务上，数据过滤应使用环境返回的确定性信号。被过滤样本中 89.3% 属于「可正常执行但返回结果错误」，此类样本语法正确、推理自洽，模型打分难以识别。
二、基于模型能力的数据过滤必然引入难度偏置凡以「模型能否做对」为准则的筛选——执行过滤、拒绝采样、自训练、强化学习的样本选择——都会系统性保留简单样本。实测保留率简单 70.0%、中等 58.8%、困难 49.1%，训练集较原始分布偏简单 5.4 个百分点。该偏置在数据中不可见，必须显式量化。
三、模仿学习的上限是教师本身监督微调的性能受限于教师能力（本项目教师为 60.67%）。若目标高于该水平，必须引入不依赖教师的信号；本项目用模型自采样加执行验证构造偏好数据，最终达到 65.45%，超过教师。
四、推理过程是「用推理时算力换训练数据」的手段数据受限时（5000 条），推理过程监督带来 2.87 个百分点的显著提升；数据充足时（全量），其效果与增加直出样本相当，而推理成本高约 5 倍。推理链的价值随数据量增加而衰减，因此消融必须在多个数据规模上进行。
五、混合推理模型的生成预算由推理过程与答案共享预算不足时推理过程会耗尽额度导致答案缺失，且被截断的恰好是最难的样本，表现形式与「模型能力不足」完全相同。本项目将生成预算设为 8192，截断率降至 2.67%，教师模型执行准确率测得 60.67%。
六、排序改善不等于贪心解码结果改变偏好优化作用于两条固定候选的相对排序，而评测指标取决于贪心解码输出。实测偏好间隔由 0.67 增至 4.81，但 92.5% 的贪心输出逐字未变。判断偏好优化是否生效必须在固定数据集上聚合测量，不能依据训练日志。
七、强化学习的可行空间由采样上界决定若样本在多次采样下全部错误，奖励恒为零、组内优势恒为零、梯度为零。基座采样 8 次至少对一次的比例为 51.76%，监督微调后升至 74.19%。「先监督微调、后偏好优化」的顺序是数据约束而非经验选择。
八、推理能力一旦内化，外挂推理即为冗余训练前开启思考模式值 13.29 个百分点；训练后值 0 个百分点（未达显著），而推理开销增加 69%。同一份能力，训练前需每次现场生成 5281 字符换取，训练后 1365 字符即达更高水平。
